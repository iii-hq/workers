Worker iii-cloud

Um worker que a pessoa adiciona ao projeto para fazer, junto com o agente dela, todo o caminho até o iii cloud: entrar, importar o repositório, deixar o app pronto, configurar a parte web e fazer o deploy. Quem quer garantia de que vai funcionar a consegue por esse caminho: o agente roda o app na máquina do jeito que o cloud vai rodar.

O que "pronto" quer dizer
plan is cleanO cloud aceitaO plano do cloud para este commit não tem bloqueio, e cada aviso foi decidido pela pessoa.
ran here like the cloudFuncionou na máquina como vai rodar no cloudO compose de produção, a versão do engine do cloud, o install congelado, o build command, o release command, todos os workers registrados, o http servindo rotas e o healthcheck respondendo.

Não cobre o container em que o cloud constrói, os valores dos segredos de produção, o tamanho da máquina e o tráfego real. Para isso, o worker acompanha o deploy e, se ele falhar, traz a evidência para o agente corrigir na máquina.

O que mudou desde a v3

  • O agente trabalha num worktree a partir da origin/main. O checkout da pessoa fica como está. Mudanças sem commit ficam de fora, e o worker pergunta se é para levá-las.
  • O agente escreve o bloco cloud: no compose. Isso pede iii 0.27.0 na máquina, porque o 0.26 recusa o bloco.
  • As correções viram um pull request, aberto com a conta GitHub da própria pessoa.
  • O deploy começa no worker. O botão Deploy faz o merge e aprova o que o cloud segura. O ambiente segue a main, sem branch de validação.
  • O cloud local (kind) sai da experiência. Ele só existe na máquina do dono, para os nossos testes.

Da v3 continua: a garantia sai do agente, sem infraestrutura nova; a parte web é uma conversa guiada; build local e envio da imagem ficam para depois.

A experiência, com o registry

As telas são ilustrativas. Os problemas do registry são reais: três vêm do plano do cloud de produção de 25/11 (can_deploy: false) e os outros, do código do cloud e do repositório.

1

Instalar e entrar

A pessoa roda iii call compose::add worker=iii-cloud no harness dela, não no projeto que vai para o cloud. O console do harness ganha a página iii cloud, e o projeto (o registry) é escolhido no passo 2. Entrar pelo navegador é o caminho principal. A API key fica para CI ou para quem só quer checar e fazer deploy de um ambiente.

2

Projeto, repositório e onboarding

A pessoa diz qual projeto (a pasta local). O worker lê o repositório pelo git remote e acha o projeto e o ambiente no cloud. Se o repositório ainda não foi importado, o agente importa. Ele trabalha num worktree a partir da branch que o ambiente segue, para não mexer no checkout da pessoa. A pessoa pede no chat. Para o registry, a recomendação é manter path://, versionando as duas pastas e baixando cada binário por sha256 no build, como o Dockerfile já faz. Nesse passo o agente também escreve o bloco cloud: (web, build, release, healthcheck) no compose de produção. Isso pede iii 0.27.0 na máquina: o 0.26 recusa o bloco e o iii compose local quebraria. Nada na máquina confere o conteúdo do bloco. Quem confere é o plano do cloud para o commit da branch, por isso o plano precisa aceitar qualquer commit.

O agente lê os candidatos que o próprio plano lista para a raiz da URL e o que o ambiente já tem, e explica cada opção em uma frase. A pessoa escolhe. Ele escreve cloud.web e cloud.healthcheck no compose, para ficarem versionados com o código, e testa na máquina.

6

Pull request e deploy pelo worker

O agente faz o commit no worktree, sobe a branch iii-cloud/ready-production e abre o pull request com a conta GitHub da pessoa. O app do cloud no GitHub continua só com leitura. O corpo do pull request leva o relatório de prontidão. Se a main andar antes do merge, o worker confere de novo.

Todo push na branch do ambiente já inicia um deploy, e isso não se desliga. Quando o plano cria recursos ou muda valores do console, o cloud segura esse deploy em "Needs your action": um push nunca aprova sozinho. Por isso o botão faz as duas coisas, o merge e o deploy com as confirmações, preso ao plano que a pessoa viu. Se alguém fizer o merge direto no GitHub, o worker vê o push e acompanha do mesmo jeito. O worker segue até o Ready, e um http sem rota conta como falha, mesmo que o cloud só registre isso no log. Se falhar, a evidência volta para o agente, que corrige no worktree e abre outro pull request. O rollback fica a um clique no console.

O worker

Fica no repositório workers, é genérico para qualquer projeto e entra no compose do harness, nunca no do projeto que vai para o cloud. Roda na máquina da pessoa ou num computer do iii cloud. O worker é fino: quem sabe o caminho é o agente, pelo perfil cloud-ready e pela skill que descreve o onboarding, os códigos do plano, a conversa da parte web e a execução na ordem do cloud.

FunçãoO que faz
iii-cloud::connectEntrar pelo navegador (código digitado) ou registrar uma API key pelo nome do segredo. Nunca recebe nem devolve um valor, e não aparece nos traces.
iii-cloud::apiChama qualquer rota do cloud como a pessoa (ou como a key). O token fica no worker. O agente usa para o onboarding, a parte web, as variáveis, os recursos e o deploy.
iii-cloud::checkO plano do cloud para um commit, mais as checagens rápidas na máquina (lock do compose, lock do gerenciador para o runtime, iii-sdk mínimo, healthcheck, variáveis sem valor). Cada problema volta como {code, file, line, excerpt, owner}.
iii-cloud::secretPede um valor à pessoa na página e grava no ambiente, ou no .env local para a execução na máquina. O agente só vê se foi gravado.
iii-cloud::watchAcompanha um deploy até o Ready. Na falha, junta eventos, logs e saúde para o agente corrigir.

O approval-gate do harness pode segurar só o deploy em produção até um clique. Ele vem desligado.

O que muda no cloud

Duas mudanças. O deploy em si não muda: o merge do pull request é o push que já dispara o deploy, e as aprovações usam o POST de deploy que já existe.

médiaEntrar pelo navegador como a pessoaO device flow do app passa a aceitar a plataforma worker, com o código sempre digitado. A sessão alcança o que o papel da pessoa permite, menos segurança da conta, membros, API keys, billing e apagar o time. Ela aparece em Devices e sai pelo sign-out que já existe. Sem isso, o worker não importa repositório nem muda configuração, porque no cloud essas escritas exigem uma sessão de pessoa.
pequenaO plano aceita qualquer commit do repositórioHoje GET /plan só planeja a branch do ambiente. O worker precisa do plano do commit da branch do pull request, antes do merge, porque só o plano confere o bloco cloud:. A leitura já resolve qualquer revisão; basta tirar a trava do plano e manter a do deploy.

Para depois, se os números pedirem

Ambiente de teste efêmero, build-check pelo cloud, build local com a receita do cloud e envio da imagem, check obrigatório no GitHub. O worker vê cada deploy depois do "Ready", então conta quantos falham mesmo assim e por quê. Se a causa for o container de build ou algo que só existe no cloud, aí vale a pena pagar por um desses.

Fases

1. O worker, a skill e as duas mudanças no cloudProva: o registry vai da importação ao "Ready" com o agente, numa cópia do repositório, e o primeiro deploy fica Ready sem nenhuma correção depois. Nada vai para o iii-hq/registry. O cloud local (kind) serve só para iterarmos rápido na máquina do dono; a prova que vale é no iii cloud de verdade, num projeto de teste, como um usuário faria. Depois, a mesma prova com um app do template Node.
2. O que os números pediremMedido pelos deploys que falham depois do "Ready".

Decisões que faltam

  • A prova final roda no iii cloud de produção? Recomendo que sim, num projeto de teste com uma cópia do registry, depois que as duas mudanças estiverem no ar. É um deploy em produção, então só com o seu OK.
  • O worker vem no template harness? Recomendo que sim, depois da prova da fase 1, para "coloca isso no iii cloud" funcionar desde o primeiro chat.
