# Changelog

## 0.9.5

- **Every wake says what it waits for.** The chat showed a wake by its label, such as `dw KAN-38 r1 w2`. Each `harness::observe` now also passes `action`, a plain phrase the chat shows instead: `Results from KAN-12 and KAN-13`, `Coding result for KAN-12`, `CI checks on PR #42 finished`, `Test suite finished`. A wake that can show while it still waits, or that can end in a failure, names the result it waits for and never says the work finished or succeeded. Labels are unchanged, and wakes are still matched by them.

## 0.9.4

- **A one-line description in the agent picker.** The `deepwork` profile's description explained the whole run (tickets, leads, waves, rounds, the dev flow) and filled the composer's agent picker with a truncated paragraph. It now says when to pick it: "Use for big goals: plans tickets, runs agents in parallel, reviews the work." The kit's own description and the README keep the full explanation.

## 0.9.2

- **A check waits for the machine instead of stopping the run.** In KAN-616 the machine ran out of memory overnight: other sessions' build output filled a tmpfs `/tmp`, swap filled, and two validations in a row died at their deadline with the database and web suites still running. The run then finished `blocked: environment` at 03:20 and sat until a person resumed it nine hours later, long after memory was freed. Now a batch check needs `min_free_mem_gb` (default 4) of available memory before it starts, `min_free_gb` also covers `/tmp`, where every long run writes its logs, and a batch the machine could not check twice in a row waits 30 minutes, looks at the machine again and retries. The run stops `blocked` only after three waits.
- **The environment re-check runs only what did not finish.** The second check of the same commit after an `env:` verdict ran every command again, formatter, linter, build and `cargo test` included (10 to 15 minutes in KAN-616 rounds 17 and 18), before reaching the suites that had not finished. Its verify task now names the first verdict with a `Reuse:` line: a command that finished there on the same commit and tree keeps its result, and only the others run.
- **A check runs only the suites its batch touched.** Each project command in the Functions text now carries `covers:`, the paths whose change can change its result (its folder, the folders it depends on, the root lockfiles and manifests), or `covers: *` when that cannot be bounded. A batch that changed nothing under a command's paths records it as `skipped:` instead of running it: in KAN-616, waves that only changed Rust crates still ran the 2,759-test web suite, 30 to 60 minutes each. A card's own Verify lines always run, and the branch review runs every command a check skipped, so the branch is still checked in full before it ends.
- **The orchestrator profile sets `follow_worktrees: false`.** With a harness and directory that read it (#1852), a worktree the orchestrator adds for a ticket never moves the orchestrator into it. Older ones ignore the key, so the `shell::exec_bg` worktree adds stay.
- **Folder rules reach the implementer and the review.** The run copied only the repository root's `AGENTS.md`/`CLAUDE.md` into the tasks, so a rule kept in a folder's own file never reached anyone: KAN-616's branch review found 17 new tests without the spec attribute that their crate's own `CLAUDE.md` requires of every test. The implementer now reads the rules files of every folder above a file before it changes it, and the review and the branch review fail a change that breaks one.

## 0.9.1

- **A worktree add no longer jails the orchestrator out of its own run.** Since the session follows a git worktree its agent creates (#1823), a direct `shell::exec` of `git worktree add` moves the orchestrator's working directory into the new worktree, and its file jail with it. In KAN-616 round 23, restoring KAN-635's ticket worktree that way left the run worktree outside the jail (`S215 path escapes the fs jail roots`): the orchestrator parked an accepted fix as blocked, and only a resend of its root brought it back. A new run would hit it at its first step, when it adds its own worktree. Every worktree add now runs with `shell::exec_bg`, which the follow does not watch, and reads its exit code with `shell::status`.
- **The listener sweep and the database recreation no longer cut a concurrent job.** 0.9.0 runs a check's Cargo and Node chains as jobs side by side, but the sweep that stops servers a killed run left behind still ran before every job, and it killed the servers of the job already running: in KAN-616 round 15 a platform suite took SIGTERM and the web suite lost its server. The recreation of the database container killed a migration check running beside the database suite in the same way. The sweep now runs only while none of the check's jobs is running, and every command that uses the database container runs in the suite's own job, after the suite.
- **A test that fails outside the batch is rerun once before it fails the batch.** Under load, the 2,737-test web suite of KAN-616 dropped one test per run, and a different one each time (`members-actions.spec.ts:116`, `deployments-worker-log.spec.ts:81`, `api-keys.spec.ts:50`). Each was in a file the batch never touched, and each passed when run alone (`deployments-worker-log` passed 90 of 90 over five repeats). The tests had run, so these were not `env:` failures, and the verifier counted each one as the batch's. Five cards that had passed review and every focused check stayed unverified for four rounds. Now, when a suite's only other failures sit outside the batch's files, the verifier reruns just those tests once, alone. A test that passes there is recorded as `flaky:` and does not fail the batch. With this rule, round 14 reran four such tests with `--last-failed`, all four passed, and the five cards landed.

## 0.9.0

Deepwork can run from the board from start to finish: started by the kanban dispatcher with no chat, asking its questions on the run ticket, ending at a pull request ready for review, telling a failing machine from failing code, and keeping to a token budget with subscription models. Each part is opt-in through an argument; a run without them behaves as in 0.8.1.

- **Questions on the board (`ask=board`).** A session started from the CLI, the board or another worker has no chat: its `harness::ask` card was accepted and waited forever, unseen. With `ask=board` every card the run would show in the chat (design, plan and finish with `approve=on`, a consequential ambiguity) becomes one `⛔ Needs you` comment on the run ticket, with the options as lines and the recommended one first, and the run ticket gets the `needs you` pill. The orchestrator waits on `kanban::on-comment` for that ticket, excluding its own comments, and goes on from the step that asked when a person replies: an option's label, a yes for the recommended one, or free text. No answer within `ask_wait_min` (default three days) finishes the run `blocked`.
- **A pull request at the end (`finish=pr`, `finish=pr-merge`).** They are the Finish answers "Push and open a PR" and "Open a PR and merge when CI is green", given when the run starts, so no Finish card is asked. They act only on a run that completes: an aborted, blocked, unverified or unfinished run, or one over budget, pushes nothing and keeps its branch. The run rebases its branch on the current base first (a resumed run whose PR is open merges the base instead, so it never rewrites a pushed branch); a conflict stops it `blocked`, with nothing pushed. The PR opens ready for review, and the CI watch first waits up to five minutes for a new PR's checks to appear (right after `gh pr create`, GitHub still reports none). `pr-merge` removes the worktree once the PR is merged.
- **In review.** A run whose PR waits for review moves its run ticket to In review, when the board has that column, with a `PR #<n>` pill.
- **Commits that read like the repository's.** The PR title is the commit a squash merge keeps: `<type>(<scope>): <what changed>`, in the repository's style, never `deepwork: …`. Batch test commits use the cards' scope (`test(<scope>): cover …`) instead of `test(deepwork)`.
- **No renames to satisfy a grep.** Cards' grep checks match whole words, and review fails a rename no card asks for whose only effect is that a grep stops matching (KAN-29 renamed `TierNotSupported` because `NotSupported\b` matched it).
- **`env:` failures.** A check that could not judge the code because of the machine (no space left, a port in use, a server or database that did not start before any test ran, a tool timeout while the tests passed) is `unsure` with an `env:` reason. The batch lead runs it once more, on the same commit, in a scope of its own, with no repair and without spending a phase. A second `env:` result stops the run `blocked: environment: …` with a `⛔ Needs you`; a resume re-runs only the checks. Before, KAN-592 spent two of its three rounds repairing a batch whose code was already right.
- **Repository rules first.** In the dev flow the orchestrator reads the repository's `AGENTS.md` or `CLAUDE.md` and copies its build, test and environment rules into every phase's `Functions:`. An environment rule a person gives during a run becomes a Follow-ups line to add it to that file.
- **`budget_tokens`.** A soft cap on the run's input plus output tokens, checked before each wave. Subscription models have no price, so `budget_usd` never tripped for them; reports show tokens beside the cost (`cost unknown, 412k tokens`).
- **Resume.** A run that stopped before its plan (a design question nobody answered) starts over from its run ticket, reading the comments after its last `⛔ Needs you` as the answer. A resume clears the run ticket's last outcome label even when the ticket is already In progress, as it is when the board dispatcher resumes it.
- **A run files its work in the board's projects and releases instead of making its own.** Every run without `project=` created a project such as `deepwork: failed deployment worker logs · 6ea0b7`, so a product's work was scattered across one project per run, and no run ever created a release: 40 small cards landed in one release with no division.
  - Project: the goal ticket's, else the existing project that covers what the goal changes; a new one only for a new product area, named for it.
  - Release: the goal ticket's, else an active or planned release that covers the goal, else a new one in the project's series (`<prefix> · R<next> — <outcome>`).
  - A plan of more than 8 items with deliverables a person could ship apart gets one release per deliverable (`<prefix> · R<n>.<k> — <deliverable>`); R, shared foundations and adopted cards keep the run's release. New items take the release of the deliverable they serve.
  - The orchestrator may call `kanban::project::list`, `kanban::release::list` and `kanban::release::create`. A project it creates keeps `lead: deepwork`, so the repository rule `deepwork-run-project` still allows it; those rules deny `kanban::release::create`, and a refused release is noted and the run goes on.

Checks that ran on real repositories (from 0.8.2 to 0.8.8, never published on their own):

- **The full database suite starts on a fresh container.** The run's Postgres container lived the whole run, and every suite left one database per test behind: after a day of rounds it held 13,648 databases and 143 GB. Suites killed at their deadline had also left 18 shared-memory segments filling `/dev/shm`, so the next suite failed 46 targets with `PoolTimedOut` and `53100` while the code was fine, and the run stopped blocked. The suite's command now recreates the container (`docker rm -f -v`, the same `docker run`, `pg_isready`) before it runs.
- **Git-ignored sources the cards cite reach the worktree.** Reviewers read only inside their worktree, and a worktree never gets ignored files, so a card citing `.planning/packages/assistant/card.md` could not be reviewed (`C215 outside jail`), and the run stopped on it. Every fresh copy (the run's worktree, each ticket worktree, every resume) now gets those files copied in at the same path.
- **A check runs its Cargo and Node chains side by side.** One job per worktree chained every command: fmt, clippy, the Rust workspace tests and the database suite, then Biome, typecheck, the build and 2,737 Playwright tests, about 40 minutes per batch, while each card took about 5 minutes to code. Chains that share no build directory now run as separate jobs at once, and a batch takes the time of the longer one (the web suite, about 25 minutes). Commands that share a build directory stay chained.
- **A long check first stops the servers an earlier killed run left behind.** Playwright starts its web servers in their own process group. Each time a check job was killed at its deadline, its `vite preview` and Prism mock kept listening, and the next attempt either reused a console built from old code or failed with `http://127.0.0.1:4298 is already used`, which cost a whole attempt. Before a long job, and after killing one, the recipe stops every process listening from the worktree.
- **A long check prints a short record.** The full suite (Rust, database, 2,737 Playwright tests) printed everything to the job's stdout. The job finished inside its deadline, but its record passed the 256 KB a function result carries: `shell::status` could not return it, and the batch was left without a verdict for a round. The long-run recipe now sends each command's output to its own log and prints only the exit code and the last 40 lines.
- **A resume runs Setup in the run worktree again.** A run's branch was rebased onto `main` between sessions, and `main` had added a Node dependency (`@iii-dev/traces-ui`). The resumed run kept the old install: web typecheck and build failed on a missing module, a validation round was spent, and no card had a defect.
- **Cargo test commands carry `--no-fail-fast`.** With three known red tests at base, `cargo test --workspace` stopped at their binary, and every binary after it went unchecked.
- **A batch repaired after a deadline gets twice the check deadline.** The same full suite (database, Rust, web) was killed at the same 40-minute mark round after round; a repair whose last validation lost a check to its deadline now runs with `2 × verify_deadline_min`.
- **Every item a discovery or a check returns becomes a card in the same turn.** The rule did not say when. A run's discovery returned 32 items, and the orchestrator created 4, keeping the other 28 "in discovery evidence until dependency-ready cards are created". Nothing created them later: they reached no round and no report, and the run stopped with most of the release never planned on the board. Readiness is already Step B's job: a card waits in To do until its `Depends on:` keys are done.
- **A database container started for the checks gets `--shm-size=1g`.** A run started `postgres:16-alpine` with Docker's 64 MiB `/dev/shm`: the DB suite crashed the server (`could not resize shared memory segment … No space left on device`), put it in recovery mode, and broke the baseline and two validation rounds. With 1 GB the same suite passes in under 9 minutes.

- **Phases can read a skill their task names.** Since 0.2.0 every lead and phase was spawned with `directory::skills::get` denied, so it started without the skills index. A task that names a skill (the Canvas and Console UI authoring guides of an application build) then stopped at `directory::skills::get is denied by policy`: in the E2E `form_flow_build`, 6 of 6 runs on Codex, on 0.8.1 and on this branch alike, ended `task_incomplete` with scores of 0 to 10. The deny lists no longer carry it, and the phase profiles set `skills_index: false` instead, so a phase still starts with no index and can fetch a skill by id.
- **Compatibility.** Every profile changed. Install between runs: a running run's leads and phases load the new profiles at their next spawn. Older orchestrators ignore `env:` reasons and repair as before.

## 0.8.1

- **A dev run starts from the remote's default branch, not from the branch you are on.** Before, the base was the branch `git status` named. A run started on a branch already merged five days earlier built on code 30 commits behind `main`: its research read an email path `main` had already replaced, and its commits conflicted when moved onto `main` for the PR.
  - The base is `git symbolic-ref refs/remotes/origin/HEAD` (e.g. `origin/main`), else `origin/main` when it exists, else (no `origin`) the branch `git status` names.
  - It is fetched to `refs/remotes/<base>` with an explicit refspec right before the worktree is created, so a narrow `remote.origin.fetch` can't leave it stale; the run branch doesn't track it (`--no-track`).
  - The PR targets, and the merge option merges into, the base without its `origin/` prefix (`main`).
  - The Plan card, or the run ticket, says when your uncommitted changes are left out; the run ticket says when commits of your checkout (unpushed, or on an unmerged branch) are.
  - The merge option says it merges into your `main` checkout, and asks you to check it out when root is on another branch.
  - A run from before 0.8.1 resumes on the `Base:` its ticket names.

## 0.8.0

The board is for the people following the run. Before, a run ticket carried comments such as `r1: done 0 · retry 0 · parked 0 · new 0 · loose 0 · cost unknown`, and its evidence was a `state::get` reference nobody could open. A card that stayed In progress for three rounds while its validation was repaired looked the same as one being coded.

- **Comments say something a person needs to know, with evidence they can open.**
  - What remains: a card's outcome, once (`✅ Verified — <what changed>`, then `Evidence` bullets with each command and its result, the commit, and a last `Raw:` state reference); `⛔ Needs you — …` with a recommendation; the Progress thread; a base branch that already fails; plan changes, cancellations, CI and merge results; and the final report.
  - No comment for a retry, a deferral, a resume re-queue, a green base check or a tier fallback. Retries and fallbacks go in the report.
  - Comments, titles and pills never use the run's own words (wave, batch `r<N>w<b>`, parked, loose end, critic, scope, tree).
- **Bookkeeping moved from comments to state.** The run pointer gets a `progress` document with the rounds, the branch review passes, the base check, the landed commits and the Progress thread id. Resume and cleanup read it instead of counting `r<n>: done`, `critic pass`, `baseline:` and `landed:` comments. A run from before 0.8.0 is read from its comments once, and resume writes the document.
- **One Progress thread on the run ticket.** A round that changed something a person wants to know adds one reply, `Round <N>/<limit> — <what changed> · next: <what happens next>`. A round that only retried for the same cause adds nothing, and the last round leaves it to the report.
- **Pills show what a card is doing now**: `working`, `validating`, `fixing validation`, `retry queued`, `needs you` (blocked, stuck, unverified or pending). The run ticket shows `round N/M`. Cards go In progress with `kanban::ticket::update`, because `kanban::ticket::move` takes no pills.
- **Tickets read from the top.**
  - The run ticket opens with the goal and the design. Args, sessions, models, base, branch and worktree move to the end under `## Run details`. Resume still finds them by their line names.
  - Every card opens with one or two plain sentences on what changes and why, before its contract lines.
  - The final report runs Result, Cards, Needs you, How to continue, Evidence, Plan, Run details.
- **Resume before the baseline.** A run stopped before its base check (a full disk) now hands its run pointer to the resuming session before running the check, so the check's wake reaches it. Before, the old owner kept the pointer and the resumed session ended on `adopted by <old>`.
- **Compatibility.** No other profile changed. Comments written by older runs stay as they are.

## 0.7.0

Lessons from one long dev run: 4 orchestrators, about 60 sessions and US$80. About 30% of the cost went to repairs and reruns, and an external review found as blockers defects the run's own critic had listed as loose ends.

- **A defect in the run's diff is a card, never a report line.**
  - A critic loose end at a `<file>:<line>` the run changed becomes a new item with a dev card, whatever its wording or severity ("minor", "needs a product decision"). One that needs a person's decision, or that is not proven, goes to Backlog as `pending`. A phase's loose ends are left alone: by contract they are what the goal doesn't need.
  - The critic proves each defect with the failing output of a check it ran, or marks it `Not proven`.
  - When the round that ran its findings verified new commits, a second critic pass reviews them. It gets `Pass: 2` with the keys pass 1 filed, and the passes are recorded in the round comments so a resume counts them.
  - New items past `max_items` go to the Follow-ups ticket instead of a comment.
  - In that run, three real defects in the diff (an ownership rule, a check during retention, a prune condition) went to the Follow-ups ticket, and the PR was opened with them.
- **Check phases get their own deadline.** `verify_deadline_min` (default twice `deadline_min`) covers verify, review, judges, the critic and the baseline.
  - The long-run recipe now measures the time left: its first call reads the clock, and the job's wake expires two minutes before the leaf's own Deadline. Before, it was a fixed 15 minutes, shorter than a 20-minute phase.
  - A check starts the project's suite and linter early, chained in one job, and runs long jobs one at a time per worktree.
  - A check whose job outlives its wake writes `unsure` with `not finished: <command>` instead of nothing.
  - In that run, a verify started three build jobs on one build directory, its database suite's wake expired, and the batch had no verdict twice.
- **Disk preflight.** `min_free_gb` (default 5, `0` turns it off) is checked before the baseline and before each batch.
  - Under it the run finishes `blocked: disk` and keeps its worktree.
  - A resume of a run stopped before its baseline runs Setup and the baseline first. A resume of a batch it stopped repairs that batch.
  - Two runs had died on ENOSPC mid-phase.
- **The run ticket's final lane says what is left.** It goes to Done only when every item but the Follow-ups ticket is done or canceled. Otherwise it goes to Backlog labelled `blocked`, `unverified`, `unfinished` or `pending` (only cards waiting for a person remain), and resume clears the label. Before, a run blocked on a full disk was shown as done.
- **Cards quote their sources.** A dev card carries a `Source: <path>#<section>: "<quote>"` line for each spec or plan its behaviour comes from, and review judges against it. In that run, most batch reviews never read the spec, and the last one could not: the spec was outside the worktree its file access was limited to.
- **Batch repairs commit as `fixup! <the batch's commit>`** when that batch committed, so they fold into it under `git rebase --autosquash` or a squash merge. A local `--no-ff` merge keeps them as they are.
- **The batch worker may run the project's lint on the packages it changed.** The lead's batch task says so too. A lint error found only by the check had cost a full review and verify round, twice.
- **`verify_model`** (default `same`) runs only the batch verify phase on a lighter model (`lead`) or a named one. Review, judges and the critic keep the child model. The adversary's description no longer says to pin a mid-tier model there: review runs on that tier too.
- **No `harness::ask` card for a blocker the run cannot clear** (a full disk, a denied permission, a missing repository): it is a comment and a `blocked:` finish. A run started by another session may have no one attached to answer a card.
- **Check phases can wait on their long runs again.** The lead's verify shapes spell out the long-run functions, `shell::on-job-finished` included: since a session may observe only functions its policy allows, a verify spawned with `harness::observe` but not the observed function ended its turn "waiting on <job>" and never woke, and the batch barrier expired with no verdict. The long-run recipe also says to print each command's own exit code: `cmd | tail; echo $?` prints `tail`'s and hid a failing database suite.
- **Compatibility.**
  - A lead from before this version reads no `Check deadline` and uses `Phase deadline`.
  - A run in progress can be resumed after updating.
  - This update changes the kit sources; an installed kit needs to be updated separately.

## 0.6.0

## 0.5.2

- With `isolation=ticket`, cards whose `Files:` share an implementation file no longer run in the same wave: the later one waits for a later wave of the same round, branches from the run branch after the earlier one is integrated, and may code while that card's batch validates. Before, both coded side by side, the second cherry-pick conflicted, and that card lost its work and waited a whole round (a conflict in the last round left it undone). `isolation=shared` already had the rule. In run KAN-456, KAN-442 and KAN-443 both changed `eval/src/state.rs` in round 6; KAN-443 was coded again on a fresh worktree in round 7, and KAN-460, which depended on it, moved with it.

## 0.5.1

- A card's scope includes its fallout: edits outside `Files:` and `Tests:` that only keep the project consistent with the card's change and add no behaviour (another use of a name it renamed, removed or re-typed, a regenerated golden or snapshot, a test or schema registry entry for a surface it added, removed or re-typed). The code phase finds and updates other uses of a name it changes, the batch worker may repair fallout on a retry, and review accepts a path outside the union whose whole diff is fallout, recording it in `checks`; anything else outside the union still fails, as does a weakened assertion. In run KAN-456, three batches whose checks were all green failed on scope alone (a schema registry, its goldens, a test fixture) until the orchestrator widened every card by comment; each cost a repair round. The harness-e2e scenario `deepwork_scope_fallout` pins it: a card that renames a field while a fixture outside its `Files:` builds the old one. On 0.5.0 the batch failed, the repair was refused as out of scope and the run ended with that card unverified and the suite red (15/100); on 0.5.1 the first batch was verified with the fixture recorded as fallout, twice (100/100), and `deepwork_batch_repair` still scored 100/100.

## 0.5.0

- Dev cards run one Code phase each. The existing wave is the batch boundary: integrate successful cards, write their regression tests together, then verify and review the combined result. `Tests:` replaces `Test first:`; test-first proof is no longer required. Plain reading/research cards keep their existing flow.
- Cards remain In progress until their batch passes, for both isolation modes. A batch rejection retries aggregate repairs and checks, without replaying all implementations. A batch still failing after its attempts no longer ends the run: the round closes and the next round repairs that batch first, with every reason; only when rounds run out are its cards parked as unverified, their changes and evidence kept on the run branch. With `verify=off`, tests are written but not checked, and cards are accepted.
- Resume adopts a batch whose lead is still working instead of stopping it: a stop SIGKILLs the phases' jobs, so a suite faulting a shared system would skip its restore. The resumed orchestrator re-arms that batch's barrier, the lead keeps working while the run pointer names its scope, and the old orchestrator is left to end on its next wake (stopping it would cascade into the batch).
- Resume continues instead of starting over: it repairs the run's unverified batch (its cards are not re-queued) and moves `unfinished` cards back to To do with a retry that builds on what is already committed. The final report says so instead of asking you to drag cards back.
- Checks judge afresh and say who owns a failure: a reason is `test:`, `product:` (only with the card, plan or spec line that ships the behaviour now) or `owner unknown:`; a suspected product defect is filed as a `pending` Backlog card, never reported as a defect. Check tasks get no earlier verdicts, and the orchestrator writes the batch task as the template, without its own method. Review fails a `Tests:` clause no assertion checks and a loosened guard or restore helper. A scenario whose setup failed covers nothing. The batch worker may run the test files it wrote when they need no external system. The baseline also runs lint and typecheck; known reds don't fail a batch. A `verified` batch is accepted only when its check verdicts agree on commit and tree. A wave's leads spawn in one reply.
- A batch grades every card. A card that passed is verified even when the batch fails (unless it shares a path with a failing card); the repair names it on a `Verified:` line and checks only the rest.
- With `isolation=ticket`, the next wave codes while a batch validates, and a card whose dependency is in that batch can start then; integration waits for the batch. A failed batch sends that wave's accepted cards back to To do with their commits kept.
- The run ticket is read less: the orchestrator's adoption check and the lead's owner check read a `dw-<R>` state pointer, which also holds the batch to repair (no more `Batch:` line in the description), and batch phases read only their cards. Runs that still carry a `Batch:` line move it to the pointer on resume. The orchestrator reads R's description through `fp::pipe` (a long run's record outgrows the 256 KB result cap), and a lead whose run has no pointer yet (an orchestrator from before it) keeps working.
- `lead_model=auto` (default) runs card and batch leads, which only relay phases, on a lighter sibling of the orchestrator's model from the same provider, read from `router::models::list`, while the phases they spawn keep the orchestrator's model (`Child model:`); with no prices (a subscription) or no lighter sibling they keep the orchestrator's model. `lead_model=same` keeps it always; `<provider>::<model>` picks any available model; a model pinned in the lead profile still wins. The choice is recorded on the run ticket.
- Found by the new harness-e2e scenario `deepwork_batch_repair`: the orchestrator grades cards from the check verdicts itself (a lead had marked a passing card failed); a dependent card's guard accepts a dependency whose commits are already on its branch (pipelining had dispatched it and the guard failed it); batch scope covers `Files:` and `Tests:` paths, and a `Tests: none` card gets no new test file; batch tasks name the run pointer on a `Pointer:` line (a lead had read its run id instead).
- Identical verification commands run once per batch. The branch review reuses suite/lint evidence only for the same commit and commands. `release=` remains board filing; it does not collect unrelated release cards for validation.
- Finish existing runs before updating: the phase and card contracts changed. A batch lead spawned before this version releases its batch when a resume changes the owner; resume such a run between batches. This update changes the kit sources; an installed kit needs to be updated separately.

## 0.4.4

- The docs and prompts no longer say a stop leaves `shell::exec_bg` jobs running. A harness and ide that reap background jobs on stop kill the stopped tree's jobs (MOT-5407); with older ones they still keep running, so workers are still told to `shell::kill` a job before their write. The orchestrator knows a parked lead whose job is killed may wake sooner.

## 0.4.3

- With `isolation=ticket`, the full test suite runs once on the run branch after each wave that landed a ticket, as a background job, before the next wave. Each ticket was verified alone in its own worktree, so two tickets that pass apart and fail together were caught only by the branch review at the end. The result is a `r<N> w<W> landed: green|red|not run` comment on the run ticket. A failure the baseline did not have becomes one `Fix: <tests> after landing <keys>` ticket, retried like any To do ticket. It gets one landing round past `max_rounds` (only those tickets, no critic), so a run that catches a red branch in its last round still fixes it. The suite is skipped, as green, when the wave landed one ticket whose Verify lines ran the same test command on the very tree the run branch now has (`git rev-parse HEAD^{tree}` equals the ticket branch's).
- Dev cards can be test corrections. A test that pins behaviour the goal or another ticket changes on purpose (one ticket pins `€10.00` while another moves the sign to `10.00 €`) is fixed in the test, not the code: `Test first: correct <test> to expect <behaviour> → passes already (test correction)`. The tests phase changes the test and shows it passes, the code phase commits the test files alone, and review does not count the moved expectation as a weakened test. Before, such a fix ended `blocked`: the tests phase refused a test that already passes and the code phase may not edit tests.

## 0.4.2

- A lead no longer copies its ticket's result into the document it writes for the orchestrator. Copies of large results came back `null` or cut down to a pointer, so the synthesis and the final report lost them. The lead's document carries `result_from` (the scope and key of the phase document with status `done`), and the orchestrator, the synthesis card's Inputs and the report read the result there with `state::get`, which the orchestrator now preloads. The synthesis runs when at least two done tickets have a `result_from`.
- The run's final comment opens with a summary of the synthesis report (its citations kept) and the `state::get` that reads the full report, instead of a retyped copy that came out shortened anyway.
- The orchestrator reads a lead document stored as a string that holds JSON as the object it holds. Leads that call `state::compare-and-set` as a native tool write `value` that way, because its schema gives `value` no type.
- With `plan_only=on` the run's last line is exactly `plan on <R>: <n> tickets; start with args: resume=<R>`.
- The README's approval rules apply only to a project that runs the `approval-gate` worker.

## 0.4.1

- The tests, code and work phases follow the long-run recipe too, so a ticket no longer fails at its first build in a fresh worktree. 0.4.0 kept them on `shell::exec`, capped at 120 s, and the leads' child deny list blocked `engine::register_trigger`, so a cold Cargo build was killed before any test ran. The deny list no longer includes it, the recipe now names a cold first build and any command that hit the cap, and `deepwork-worker` (the base of `deepwork-impl`) preloads `shell::exec_bg`, `shell::status`, `shell::kill` and `engine::register_trigger`. A Verify line that is a long run keeps its command, args and `cwd`.

## 0.4.0

- A parked parent now reacts when a child ends: a lead whose phase child ended without its result fails that attempt at once (`no result: <status>`), and the orchestrator closes the key of a lead that ended without one so the wave barrier still closes. Both use the `child ended` notice that a harness sends to a parked parent; older harnesses never send it, and the deadline wakes apply as before.
- The busy check no longer reads a `completed` session with `expects_wake:true` as working. The orchestrator resumes a lead whose phase child has ended and whose key is already in the scope (a wake that never arrived) in the same session with a `Resume:` task; the lead handles that task and carries `engine::unregister_trigger` and `harness::triggers::list`.
- The run stops, naming the folder to start from, when the files the goal or its ticket names (or the repository it names) are not under the repository root. It never searches the disk for the repository.
- Long commands run as background jobs. The baseline, the branch review's full suite and linter, and any verify step that needs more than ~90 s use `shell::exec_bg` and a `shell::job-finished` wake instead of `shell::exec`, which is capped at 120 s: the agent registers the wake, ends its turn, and reads the exit code when it fires. Every lead task ends with the recipe. Verify spawns now allow `shell::exec_bg`, `shell::status`, `shell::kill` and `engine::register_trigger`, and the critic's deny list no longer includes `engine::register_trigger`. Requires `ide` `>=0.12.19`, the first synced release known to carry `shell::job-finished` and its replay.
- Review checks behaviour, not only scope: for each new branch, state, effect or caller it names an input that would break it and reads the code that handles it. A confirmed defect is a rejection with the reason `<file>:<line>: <input> → <observed wrong behaviour>`, and a reason that starts with `test:` makes the lead run the tests step again first.
- A defect in the run's own diff is a new item, never a loose end. Workers and the critic report it as a `new_item` (a fix card whose `Test first:` is the input that shows it), and a worker fixes a one-line defect inside its own `Files:` in its phase.
- Loose ends are one line each (`<file>:<line>: …`) and no longer become tickets. They are kept for the report, one that names an existing ticket becomes a comment on it, and the finish creates one `Follow-ups: <goal>` subtask in Backlog, labelled `pending`, with a checklist (`- [ ] <line> (<source>, <commit>)`). The round comment's `loose <n>` counts lines.
- Existing tickets are adopted, not re-created. A live ticket the goal, the run ticket or its comments name becomes a subtask of the run ticket with its card appended; a card that would open with `Fixes <KEY>` or `Part of <KEY>` is that ticket's card; a goal that is itself a ticket key makes that ticket the run ticket. The design step asks only when the user's text and the board disagree, and added work in a replan follows the same rule.
- The finish card gains "Open a PR and merge when CI is green". Both PR options then run a Land step: `gh pr checks --watch` as a background job (up to an hour), a squash merge on green for the merge option, one `Fix CI: <check>` ticket and a round when a check fails and rounds remain, and `CI: <state>, PR open` otherwise. A repository with no checks counts as green. The card holds at most four options (`harness::ask`), so discarding the branch is now the typed answer `Discard`. A merge happens only on the user's finish answer, and a run never deploys or writes to production unless the latest message asks for it.
- Dev flow runs call `browser::doctor` once when the goal needs a browser and the function exists; on `ok:false` the Plan card carries `preflight: browser: …` and the run goes on.
- The cost line is `≥ $C` from `totals.cost_usd`, with `incomplete (<provider/model> unpriced)` for each `by_model` row that has `cost_complete:false`, or `cost unknown` when the total is null. The flag takes effect with a harness that reports `cost_complete`; an older harness reads as before, minus the fallback that summed `by_session`.

## 0.3.0

- One worktree per code ticket (`isolation=ticket`, the default in the dev flow): each impl-tier ticket is dispatched into its own worktree `.worktrees/<slug>-<key>` on a branch off the run branch, rebased on it for a retry (a conflicting rebase starts the ticket over in a fresh worktree, with the old commits kept on a reference branch until Finish), and landed on it with a cherry-pick once verified, or accepted with verify off; a conflict is a rejection retried next round on the new base. Tickets that share a file or a test target no longer wait for a later wave, and commit hooks no longer force one ticket per wave. `isolation=shared` keeps the 0.2 behaviour.
- `approve=on` now also gates open design questions and the plan in the plain flow, not only in the dev flow. `plan_only=on` plans without dispatching: the run ticket and its cards go on the board, and `resume=<R>` starts the run later.
- `synthesize=on` (the default in the plain flow) ends a run, when at least two tickets are done with a result and the run was not stopped, blocked or over budget, with one `Synthesize:` ticket that merges their results into a single report, every claim citing its ticket, verified like any other ticket; the report opens the run's final comment. The planner no longer plans its own merge item.
- `resume=<R>` adopts an earlier run from its board state: goal, args, flow, branch and worktree come from the run ticket, In progress tickets whose lead is gone are re-queued (a lead that is still running is stopped first), and the rounds continue. A finished run resumes the same way once cards are back in To do.
- Dev cards' `Verify:` lines carry no `cwd`: every agent runs them in its own worktree. A fresh ticket worktree gets the install step the repository needs before it builds (a Node project's offline install); build output is never shared between worktrees.
- The verifier treats a test command that ran no test (`0 passed`) as satisfying nothing.
- Lead spawns spell out the 48-character limit of the session name (the key and ` · ` count), which runs with long ticket titles hit.

Bounded rounds, a completeness critic and an optional soft budget.

Design and plan approved through `harness::ask` (`approve=on`), test-first code tickets (`deepwork-impl`: `Files`, `Test first`, `Implement`, `Verify`, `Commit`), one git worktree per run with one commit per code ticket, a code review of every commit (research tickets run work then verify, without a commit), a branch review (full suite, linter, whole diff), loose ends filed as `pending` Backlog subtasks, and a finish you choose: merge, PR, keep or discard.
