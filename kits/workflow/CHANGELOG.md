# Changelog

## 0.1.16

- **Pull requests name no board ticket.** A run opened #1944 as `feat(claude-code): KAN-156 read and watch external session replies`, and its body named three more keys, four times: a `## Tickets` bullet each for KAN-157, KAN-158 and KAN-159, and `Branch review findings were filed as KAN-159`. Those keys belong to the local kanban board: on GitHub they point nowhere, and a squash merge keeps the title in the history. The kit wrote them on purpose: the title was `<type>(<scope>): <run ticket> <what changed>` and the body was the board's report. The title is now `<type>(<scope>): <what changed>`, and the body is the report for the pull request: the same sections, each ticket named by its title (`- **<title>**: <outcome>, <one short clause>`), with no `[KEY]` citation, no `resume=` line and no line that names the run ticket. A resumed or continued run and a Fix CI round update the body the same way, and a title a person fixed still stays. The run ticket's report comment and the final message keep their keys. The README said the key in the title let the control plane link the pull request to the card, but nothing read it: the run ticket keeps that link with its `PR:` comment and `PR #n` pill. Measured on an isolated stack with a recording `gh`, a simple goal with `finish=pr`: 0.1.15 put a ticket key in 4 of 4 pull request titles and 1 or 2 keys in every body; 0.1.16 put none in 4 of 4, and both kept code and commits free of keys.
- **No ticket key in code or commits.** Only the implementer had the rule: never a ticket key in a commit message, code comment, docstring, test name or fixture (#1944's 19 files and 46 commits named none). The worker, and through it the planner, now follows it too, and so do the orchestrator's own direct changes and commits and the **Commit** bullet of every card it writes, a Fix CI card's included; a run branch's name never carries a key. The batch check fails a line the change adds that names a key of this run (the run ticket, a card of the batch, a card already checked in its range, a card a split moved), in any letter case and with `-` or `_` (`kan_12` in a test name), never a token of the same shape such as `UTF-8` or `SHA-256`, nor a key the base already holds as data (a kanban fixture's `KAN-1`), and not with the board off, whose `T1`, `T2` are no keys. The same key in a commit message is a note, since history is never rewritten.

## 0.1.15

- **A long run is stopped by its budget, not by a round count.** In a live session on 2026-11-26 (Codex gpt-6.2-astra) one UI card ran 18 work and check passes in 10 workflow runs over 10 hours, and you had to press Continue 3 times only because `max_rounds=3` ended the session at each round limit: each `continue` buys `max_rounds` more rounds, and a bare `continue` does not read new args. `max_rounds` now defaults to 12 and stays the hard cap, and `budget_tokens` defaults to 4000000: input plus output tokens of the session tree, which subscription models report even when their cost is unknown. The report's Run line names the budget when it was the stop. Your own value wins, `budget_tokens=` with no value turns it off, and a `continue` after a budget stop gives the run one more budget.
- **A check that keeps finding new things asks you.** That card never passed: 37 distinct failure reasons and none repeated. Each pass fixed what it was given and the next check found 1 to 4 new ones, at least 6 of them regressions of the previous fix, and the diff grew from 895 to 2216 lines, while the card's own Verify calls, lint, typecheck and tests were green in rounds 11, 15 and 17. Now, when the check of the same cards fails for the second round in a row, no reason repeats the previous round's, every reason is a review finding (`product:`, `lean:`, `test:`, `standard:` or a `file:line` finding) and the Verify calls and project commands pass, the run starts no repair and asks a Moving target card: accept the cards (recommended: they end unverified with their commits on the branch, and every open finding goes to the Follow-ups ticket), split the cards (next entry), keep repairing (the card comes back after two more such rounds), or stop the run with the cards unverified, kept for a resume. The run pointer keeps the count, so a resume does too. A session started by another session takes the recommendation.
- **A card that keeps failing on one part can be split.** KAN-158 was checked 18 times as one card (17 fails and 1 unsure), and from the second pass of round 14 on, 8 of the last 12 reasons were about hiding external sessions, a line nobody had asked for, while the viewer and Fork waited on them under one verdict. The Moving target card now also offers split the cards: each part the open findings break, with its Acceptance sentences and Verify calls word for word, becomes a card of its own, and the rest is checked again at once. That check reads a `Moved:` line and leaves those findings to the new card. A reason that names no part (a `lean:` or `standard:` finding, a failing command) stays with the card, and a card whose every Acceptance sentence is broken is accepted, not split. Accept stays first and recommended, so a session started by another session, which takes the recommendation, never splits a card.
- **Findings no longer rewrite a card's Acceptance.** In that session the orchestrator itself added an Acceptance line to the card, from a check's finding, while writing your answer to a scope card, and every reason of rounds 15 to 17 was about that line. The orchestrator now never adds, widens or rewords a card's Acceptance, Implement or Scope bullets from a finding of a check, the review or a refuter: a finding is a reason for the next repair, a new item or a loose end. Only your own words (the goal, an answer to a card, a comment) change Acceptance, and an answer adds only what it says. A new item that a To do card's Acceptance already states is dropped, no longer folded into that card.
- **Each Acceptance item checks one behaviour.** On an isolated Codex stack on 2026-11-27, with the goal "add slug(text) and titleCase(text) to src/format.js, with tests", the orchestrator wrote the focused run's card itself, and in 7 of 8 sessions gave it one Acceptance item for both functions (one `node` call printing both results) and one whose only Verify call was `npm test`. Split the cards had to move slug's criterion together with titleCase's, and the card kept only the `npm test` item, so its next check proved no behaviour of its own (this release no longer splits such a card: it ends unverified, as accept the cards ends it). Only the session whose card had one item per function split it correctly and checked the rest for real. Every card the orchestrator or the planner writes, at the start or mid-run, now states one behaviour per Acceptance item (one function's result, one thing a person does on a page, one answer: the input and the expected result, or the observable effect), each with its own Verify calls. A line that decides nothing ("handles edge cases", "robust") is not an item, and neither is a run of the project's suite, build or lint: the batch check runs them. Split the cards still moves Acceptance sentences word for word. With this rule, 5 of 5 cards on the same goal had one item per function, and split the cards moved titleCase alone in 3 of 3 sessions, leaving slug checked on its own item.
- **Cards are checked before their first dispatch.** On the same stack and day, with the goal "add slug(text) and titleCase(text) (first letter of each word upper-case) to src/format.js, with tests" and a real check, 2 of 2 sessions reached the Moving target card at round 2, each check finding a titleCase word boundary the card never decided: an em dash in "hello—world", an apostrophe in "6'wide", digits in "mp3s", the Catalan middle dot in "col·laboració". Nothing was found on slug. The only adversarial step before work was the design panel, which attacks designs, not the cards written after it; the focused path, `design=lean` and work added mid-run had none. Now every card is checked once before its first dispatch, all of a round's new cards in one read-only node on the plan model (`Mode: cards`): it names an Acceptance item that joins two behaviours or has no Verify call of its own, words that decide nothing, and, for each behaviour the card states, up to five inputs a careful reviewer would try first that no item decides, each with the simplest expected result. The orchestrator writes each input it can decide into the card with its own Verify call, records it under Notes and in the decision log, and asks you every consequential one on an Edge cases card, four questions at a time, before its card runs (a session started by another session takes the recommendations). The check never adds a behaviour, widens the scope, changes what you decided or rewords a card you wrote, and it ends before the card's first dispatch: from then on findings still never change Acceptance. A check that fails or times out leaves its cards unchecked, and the run goes on. It costs one more run of one node before the first wave, and before the first wave of a round with new cards. Measured on the same goal with a real check: with the card check, 2 of 2 sessions passed on their first work run (8 minutes, about 190k tokens); without it, 3 of 5 passed (two of them on a second run) and 2 stopped at the Moving target card (14 minutes, about 435k tokens). On a goal with nothing to decide (slug alone) it added about 2 minutes and 40k tokens.
- **Changed.** `max_rounds` defaults to 12 (was 3) and `budget_tokens` to 4000000 (was none). A run ticket an older kit wrote with the old defaults resumes with the new ones: pass `max_rounds=3` or `budget_tokens=` to keep the old behaviour.

## 0.1.14

- **Nodes can load a skill their task names.** Every run started its nodes with `directory::skills::get` denied, and the worker profile said "a node may not read skills". A ticket that required `/skill:impeccable` before any UI edit ended `blocked` with nothing edited, and `FAILED: directory::skills::get is denied by policy` reached the user. The deny list no longer carries it, the rule that barred skill reads now only covers the browser calls it was written for, and a node loads each skill its task, card or comments name before the work it governs. The card and the node's rules win where a skill conflicts with them.
- **Nodes still start with no skills index.** The denied call was what kept the index (about 10k tokens with 276 skills installed) out of every node. `skills_index: false` on the node profiles now does that.
- **The run can land its pull request.** Through 0.1.13 a run ended once its pull request was open: the kit never watched its CI and merged it only when you asked. The Finish card now also offers `Open a PR and merge when its checks pass`, and `finish=pr`, `finish=pr-merge` or `finish=keep` on the `args:` line gives the answer when the run starts, with no card (`pr` and `pr-merge` only for a run that ended done; any other run keeps the branch and the report says why). Once the pull request is open the run watches its checks. Green squash-merges it under the merge option, comments the merge commit on the run ticket and removes the run worktree; otherwise the pull request is left ready for review, and on a board with an In review column the run ticket waits there under a `PR #n` pill. A pull request that still reports no CI checks after five minutes is never merged on its own: the kit cannot tell a repository with no CI from checks that are late, so it leaves the PR open with `CI: no checks reported, PR open`, and your words then merge it. Red gets one `Fix CI: <check>` ticket, built from the failing log, while rounds remain, and that round's report pushes and watches again with no card. Merge, discard and CI results are commented on the run ticket.
- **Questions are cards the board can answer.** Every card marks one recommended option. With the board on, a card names the ticket it blocks: it shows on that ticket with a `needs you` mark and in the control plane's question box, and the session is linked to the run ticket. A card waits three days, then tells the agent nobody answered and stays open: nothing is decided for you, a late answer still counts, and a run that cannot go on without it ends `blocked: no answer to <header>`. The one exception is the Run health card (below), which takes its default after 30 minutes. An answer typed in the chat withdraws the open card first. A ticket blocked on a question only you can answer is asked on one card while the run goes on, and your answer puts it back in To do. Choices the agent made alone also go to the board's decision log.
- **Board dispatch.** A kanban `dispatch` rule with `assignee: workflow` starts the Workflow agent on a To do card of a mapped project, with no chat: the card is the goal and becomes the run ticket, and the brief's card waits on it, so the run starts when someone answers there. Give the rule a `model`: the profile pins none. `args: finish=pr` (or `pr-merge`) on the rule opens the pull request with no Finish card, and a run ticket dragged back to To do is resumed, not started again. The run ticket's `Orchestrator session:` bullet is now a plain line, which tells the dispatcher which session owns the run. The rule's fields are in the kanban README's Board dispatch section.
- **A run's project no longer waits for a person.** Since 0.1.10 a run on the board is filed under a project, but this repository's and the kanban worker's approval rules sent the create to a person, and a refusal left the run with none. The new rule `workflow-run-project` in `iii-permissions.yaml` and `kanban/iii-permissions.yaml` allows a `kanban::project::create` whose `lead` is `workflow`, as `deepwork-run-project` does for deepwork. Every ticket the run creates is now filed under that project too, the Synthesize and Follow-ups tickets included, and so is a ticket the run adopts that has none: a subtask does not take its parent's project, so until now only the run ticket was in it.
- **A check that could not judge is run again.** A check that ran out of time runs again at once, alone, with twice `verify_deadline_min`, and keeps what the commands that had finished printed at that commit. When it runs out of time again, a Run health card asks whether to retry only the unfinished checks, retry with a longer deadline or stop the run with those cards unverified. Its default, taken after 30 minutes, is the longer deadline when the lost checks show a command needs more time than the deadline (on the isolated stack a 15-minute suite under a 3-minute deadline was retried twice at 3 minutes before this), and then the deadline is what that command needs plus 5 minutes. A command the machine stopped (no space, a port in use, a service that did not start) is run once more inside the check; when it stops again, the run waits 30 minutes for the machine and checks again, three times at most, then ends `blocked: environment` (`blocked: memory` under the memory floor) with the batch kept for a resume. New `min_free_mem_gb` (default 4; `0` turns it off, and a host without `/proc/meminfo`, such as macOS, skips it) holds a batch check until that much memory is available, and `min_free_gb` now also covers `/tmp`, where long runs write their logs.
- **Checks skip what the batch did not touch.** Every project command of a run carries `covers:`, the paths whose change can change its result, and a batch check skips one whose paths the batch did not touch. The branch review first runs the commands no check of the run ran (0.1.9: it ran none); with no review (`critic=off`, or one verified ticket) they are not run. A test that fails in a file the batch did not change is run once more, alone, before it fails the batch (`flaky:` when it passes), and a Cargo test command carries `--no-fail-fast`, so one red test binary no longer hides the ones after it. A command that failed for cards sent to Backlog unverified joins `Known red at base`, so no later batch of the run fails for it.
- **Checks catch a test bent to pass.** The check fails a guard or precondition loosened so a test passes, a test the change did not add that it skips, deletes or leaves asserting less, and a rename or rewording whose only effect is that a Verify grep stops matching. The planner writes a grep for the absence of a name as a whole-word match, and no card asks for a rename to satisfy a check. A person's comment that adds or changes a requirement is a criterion of its card, and a probe of the check's own that cannot run decides nothing. For each branch the change adds, the check tries one input that would break it, taken from what the card or a caller can send: an input outside that (a script or encoding the card does not name) is a note, never a fail. Unbounded, the probe ran a "remove accents" goal for 8 rounds over non-Latin marks. A loose end the branch review finds on a line the run changed becomes a ticket of the run, not a report line.
- **Folder rules are standards.** The `AGENTS.md` and `CLAUDE.md` of every folder above a changed file bind the implementer, the check and a direct change, for the files under them. The repository's top `AGENTS.md` and `CLAUDE.md` are read before the run writes its commands, so their build, test and environment rules (a port, where a database or build output goes) are in every command the nodes run. A build, test or environment rule you give during the run that those files lack becomes a line of the Follow-ups ticket, to add it there so the next run reads it.
- **Long runs in the nodes.** `workflow-worker` (and through it `workflow-impl` and `workflow-planner`) and `workflow-verifier` run one long job per build directory: chains that share none run as separate jobs at once, one wake per job. The job wake's `action` says what finished, and its expiry is computed from a clock read in the same reply. Before its first long job, and after a kill, a check stops the servers a job of the run left listening (where `ss` exists): every job of the run carries `WF_JOB` in its environment and only listeners that inherited it are stopped; any other server there keeps running. An implementer may run a formatter on the files it changed.
- **The board shows more.** A Backlog card that is blocked or unverified carries a pill, the run ticket shows `round N/M`, a ticket's outcome comment lists the commands of its check and what they printed (it said `run <run id>`), and board text says `validation of <tickets>` for a batch check, `branch review` and `base check`. With the board on, every node session that names no ticket of its own is labelled with the run ticket's key, so the board's project tree shows it under the run ticket. The Workflow agent's timers name what they wait for (`action`).
- **`budget_tokens`.** Stops dispatching once the run's input plus output tokens reach it. It works with subscription models, whose cost is unknown and which `budget_usd` never stops. The report's Run line gives the tokens beside the cost, and after a resume in a new session the cost says `this session`: it counts that session's runs only.
- **Resume and replan.** A resume in a new session adopts a run that is still working instead of stopping it, and refuses while the earlier session is in the middle of a turn or its status cannot be read; a session that lost its run to a resume disarms its own wakes, writes nothing else and ends `adopted by <session>`: every pointer document names its writer, and the resume rewrites all of them, so the earlier session cannot write any of them again. A full run that a resume or `continue` picks up runs its install again before its first check, since the branch may have moved. A card queued again keeps the commits on its ticket branch. A plan change in the chat rewrites or cancels queued cards; a card that is running finishes as it is and gets an `Align <KEY>` follow-up. In a dev run a `Discover:` ticket runs as a work and check pair in the run worktree, with no commit and no batch check. A goal that is the key of a subtask stops at the brief and names its parent, since kanban takes no subtask under a subtask.
- **The report says how to go on.** When work is left, its last lines say that `resume=<run ticket>` re-queues the unfinished cards and repairs or re-checks a batch that waits for it, and that a failed or blocked card runs again only after you drag it to To do. A run keeps one Follow-ups ticket, across resumes too, and that ticket no longer holds the run ticket in Backlog as `pending`: a run whose only leftover is a follow-up ends Done. The run's ticket branches are deleted with their `-r<N>` copies.
- **Changed.** A dev run starts from the remote's default branch: what `origin/HEAD` names, else `origin/main`, and your checked-out branch only when the repository has no `origin`. Through 0.1.13 it started from the branch you were on, which can be days behind or already merged. The base is fetched right before the run worktree is created and the run branch does not track it. Uncommitted changes and local commits the base lacks are left out, and the run ticket's Notes say so (the Plan card too, under `approve=on`). A push publishes only the run's own commits, and a pull request or a local merge targets the base branch by name. A base that is only behind its remote is no longer a card (the card remains for code on a branch the base does not hold), and `Merge it into <base> and start` is now `Land it on <base branch> and start`, which on a remote base merges that branch's pull request once its checks pass, then starts the run. The Finish card recommends `Keep the branch`, and `Discard` is now a typed answer under `approve=on`, not an option. Before a new pull request opens, the branch is rebased on the current base, and a conflict pushes nothing. The title is `<type>(<scope>): <run ticket> <what changed>`, at most 72 characters, so the control plane links the pull request to the card; a pull request that already exists gets only its body updated (0.1.9 also rewrote its title). A check that ran out of time or that the machine stopped is run again instead of parking its cards `unverified` at once, which reverses part of 0.1.9; any other check that could not run still parks them. The profile's `description` is one line (the long text stays in the kit manifest), and watching CI is off the README's list of what to use deepwork for.
- **Compatibility.** Requires `harness` 1.10.0 (durable `harness::ask` cards with `about`, a recommended option and an expiry; `harness::ask::list`, `harness::ask::withdraw`, `harness::link-card`) and `kanban` 0.2.7 (board `dispatch` rules, from 0.2.6; questions mirrored on the card with their `needs you` mark, a dispatcher that does not park a card waiting on an answer, and `kanban::question::record`). iii/deepwork asks for kanban `^0.2.6`, so the two kits still install side by side. The profile's `functions:` gains `harness::ask::withdraw`, `harness::ask::list`, `harness::link-card`, `harness::status`, `kanban::question::record` and `state::compare-and-set`, and loses `state::set`: the run pointer is written with a compare-and-set, so a resume and the session it took the run from cannot both write it. A policy that narrows the Workflow session's functions must allow them, with the `harness::on-timer` and `shell::on-job-finished` wakes. Update between runs: a session opened before the update keeps the 0.1.13 profile, so start a new session with `args: resume=<run ticket>` to go on with a run. A run ticket 0.1.13 wrote is resumed as it is, its `Orchestrator session` bullet included.

## 0.1.13

- **The agent runs the git operations you ask for.** A typed `update main`, `git pull`, `create the branch and switch to it`, `rebase it on main` or `push` was refused, with the command handed back for you to type: the profile let the agent move your checkout, merge or push only at the end of a run, whatever you said. Your own words, or a card option you pick, are now the permission, on any branch, in your checkout, before, during and after a run. The agent looks first, takes the form that loses nothing (`git merge --ff-only`, explicit paths, a push without force) and says what moved, then goes on with the goal that waited for it.
- **A loss is still yours to name.** Dropping uncommitted changes or commits nothing else holds, or rewriting a published branch, runs when your words name what goes (with `--force-with-lease`, never `--force`). Vaguer words, such as `clean the repository`, get one card first that lists what would be lost. A conflict or a refusal puts the tree back, quotes git and asks.
- **A base that is behind is a card.** A goal that needs an operation before it can start, such as a base behind its remote without the code the goal builds on, gets a card with that operation as its recommended option, instead of a command for you to type.
- **A push you asked for is not asked again.** A push, a pull request or a merge you asked for in words, in the goal or later, is done after the report with no Finish card, when no ticket ended failed, blocked, unverified or unfinished and the push publishes no other commit of the base. Otherwise the card asks it and says what it carries.
- **Changed.** A small change whose goal also asks to commit or push it is done directly. A change wanted on its own branch or as a pull request is still a run. A new goal on top of an unmerged run branch can now be answered with `Merge it into <base> and start`. A session started by another session gets no push, pull request or loss on that session's words, as before.

## 0.1.12

- **The agent briefs you before it builds.** The interview used to sit deep in the setup of a run, after the goal was sized, and a run whose goal looked settled to the agent started with no question. It is now the second thing the Workflow agent does with every goal that is not a small direct one. A few lines say what it understood and what it found in the repository and in the files you gave it, and one card carries the rest: the decisions only you can make (at most three a round and three rounds, the recommended answer first), then `Start`, which says what you get and the paths that change, the choices the agent made for you and what it leaves out. A goal that adds records or content always asks the form it is delivered in, such as a migration like the last one, entry by hand or a file. Nothing is created before your answer. The `Path:` line comes after it, and the work starts in that same turn. A question, a lookup and a small direct change get no brief and are as fast as before.
- **Your material is read before the first question.** Files and text you give the agent to build from are read to their end before the brief, which names any it did not. How much of them the result keeps is always asked.
- **The run is held to the brief.** The brief and your answer, quoted, open the run ticket; the agent's own choices are listed as its calls, never as yours. Every thing the brief promises is an acceptance item of some ticket, and a ticket drops only what the brief said it leaves out. A ticket built from files you gave names each one that reads as text and the call that reads it: its node and its check read the file itself, and the check fails a result that lacks what the ticket says it keeps. A goal that took several messages keeps all of them on the run ticket.
- **No data typed into a running copy of your product.** For a goal that adds records or content, the agent lists the repository's seeds, fixtures and latest migrations and reads the one that loaded the nearest. It creates or changes data through a running application's pages, API or database only when your own words, or a card option you pick, ask for exactly that.
- **No turn ends on "not done yet".** A reply with no call ends a turn, so while a goal is unfinished one is sent only with an open card, an armed wake, a report or an answer. A read-only step that would answer your question is taken, not offered as a next step, and work the goal does not cover is named, not started. Before a run exists, `continue`, an answer or a correction goes on with the goal the agent already holds.
- **Changed.** Every run now waits for one click, also when nothing is open, and a focused run asks every open decision about what you get, not only the consequential ones. An unsure judge answer no longer adds a Project question to the card: the run goes under the repository's project, as a focused run already did, and `project=` picks another. `run it as a workflow` after a partial direct report gets its brief and its card too. A session started by another session still takes the recommendations and goes on, and so does a goal that says not to ask (a consequential decision left open ends both `blocked`); the run ticket and the report say the brief was not approved. A script that drives a session nobody watches answers the card with `harness::ask::answer`, or says in the goal not to ask.

## 0.1.11

- **The judge reads the goal as you wrote it.** To pick a run's project, the Workflow agent sends the goal to the `judge` worker. It used to send a short sentence of its own, and the judge was often not sure enough about it. A focused run whose goal no theme covers then went under the repository's project instead of a new theme project. The agent now sends the first 200 characters of the goal, word for word: never a summary or a translation. It leaves out the `args:` line and a sentence that only asks for a workflow run. This is what the README already said a hosted judge provider receives; a local judge, or `project=`, keeps it on the machine. For a goal that is a ticket, the agent sends the first 200 characters of the ticket's title and description, and the README now says so.

## 0.1.10

- **Runs are filed under fewer projects.** A run on the board no longer creates a project of its own: it goes under an active project that fits its goal, and a project stands for a product or a theme. With the `judge` worker, the Workflow agent asks it once which project fits. A confident answer is used, a goal that fits none gets one new project named after its theme, and an unsure answer is one more question on a full run's interview card. Without the judge, or when its call fails, the run goes under the repository's project, named after the repository and created once. A repository's project is never one of the judge's choices, so a goal no theme covers gets a new theme project. With the judge installed and no theme project on the board yet, the run opens one without asking. `project=` still wins, a goal ticket keeps its project, and a resumed run keeps the run ticket's. A name that belongs to an archived project is not reused: the run goes without a project and the run ticket says how to fix it. Until now every run added a project named `workflow: <goal> · <session>`; those are never picked, so archive them.
- **Titles drop the `workflow:` prefix.** The run ticket's title is the goal, and no project is named after a run. The `wf:run` label marks the run ticket, and its new `Project` bullet says how the project was chosen.
- **The judge is optional.** The kit does not list it, and a run works the same without it. With a hosted judge provider, the first 200 characters of the goal, the repository's name and the names and descriptions of the active projects are sent to it; a local judge, or `project=`, keeps them on the machine.
- **A focused run goes on the board.** With `board=auto`, a run of one or two tickets now gets a run ticket with its plan and its cards, filed under a project like any other run, and it can be resumed. Before, it ran off the board and left no ticket. It still has no baseline, and no design run when the place is known. `board=off` keeps a run off the board.
- **With the board off, no task names a run ticket.** Design and review nodes were told `Run ticket wf-…` and looked that name up on the board (`ticket not found`). Their task now carries the goal and the run's name only.
- **Nodes read the long-run recipe from their own profile.** The Workflow agent typed the recipe into every node task and sometimes shortened it. `workflow-worker` (and through it `workflow-impl` and `workflow-planner`) and `workflow-verifier` now carry it themselves, and a task's `Functions` block holds only the project's commands and its `Standards`, `Browser` and `Known red at base` lines.
- **A parallel wave starts in the session that planned it.** Creating the run worktree used to move the orchestrator's session into it, and the first wave with two or more tickets was refused until the run was resumed from a new session. The session now stays in the repository's top folder.
- **A node keeps the engine's variables.** When a node lists the environment before it runs project code, it unsets the variables that point at production and leaves `III_*` alone. Before, it sometimes unset `III_URL` too, which would break a project command that calls the engine.
- **The environment is listed before any project code runs.** The rule now names the moment, and the implementer's `Run first:` command comes after it. Before, a node that judged its command harmless could skip the listing.
- **Node profiles no longer point at the opening message for the result.** They say "as your instructions say", which is right wherever the workflow worker puts the result contract.

## 0.1.9

- **The review's findings are fixed in the same run.** Subtasks the final review creates get a round even when `max_rounds` is spent: one more at most, since the review runs once and whatever fails in that round is parked. Before, findings that arrived on the last round were parked `unfinished` and waited for you to type `continue`. `budget_usd` still bounds the cost when the provider reports one.
- **A node's task is its template and nothing more.** The Workflow agent fills the slots of each step's task and adds no instruction, caution or limit of its own, and a verdict's reasons reach the next attempt as the check wrote them. What a run learns about the project's commands (a variable or flag one needs, a failure reproduced at base) goes into the `Functions` block of every later task. Text added to tasks had sent work nodes into the check's job until they timed out.
- **A work node no longer does the check's job.** An implementer never runs the project's full suite, build or lint, and in a batch never opens the page, also when a reason names one: the check runs them. It answers as soon as its commit is made.
- **No node deploys or touches production unless its card asks for it.** `workflow-worker` (and through it `workflow-impl` and `workflow-planner`) and `workflow-verifier` say it themselves: never deploy, and never point a command at production or real user data, unless the card asks for it. Until now only the Workflow agent's own rules said so, and nodes depended on text it pasted into their tasks. A node that runs project commands first lists the environment's variable names and unsets any that point at production.
- **A repeated check no longer fails a card on lines its last check read.** A new lean or missing-coverage finding on a line the repair did not change is a note in `checks`, not a reason, when the pass before it was a full check. A product defect, a failing command and a reason the last verdict carried still fail the card.
- **The review does not run the suite again.** The critic reviews the range and proves each defect with a check of its own.
- **A batch check over uncommitted files answers at once.** When the worktree has uncommitted paths, the check answers `fail` with `uncommitted: <paths>` and runs nothing else, instead of a full check whose result could never be accepted. That is what a work node that timed out in the middle of an edit leaves behind.
- **A workspace test run that stopped at its first failing package is completed.** The check runs the packages the runner did not finish by themselves before it answers, so their failures are in the first verdict.
- **Long runs keep their output out of the conversation.** The long-run recipe sends the output of each command of a check to a log in a temporary folder and prints its exit code and last 40 lines; a node reads more with `tail` or `grep`. A full suite's output no longer exceeds the result size limit or stays in the node's context for every later turn.
- **A card the check could not verify is parked at once.** In a batch, an `unsure` verdict that is not a blocked claim (a check that could not run) sends the cards it did not verify to Backlog as `unverified` in that round, instead of keeping the batch in repair round after round. The review can then run. A blocked claim keeps its repair path.
- **A check your machine cannot run is put to you once.** When the baseline could not run a check for lack of something only you can supply or allow (a download, a credential, a service), the Workflow agent asks one card before the first wave: supply or allow it, or deliver the tickets that need it `unverified`. The answer is recorded under the run ticket's `Decided by the user`. With nobody to answer, those tickets are delivered `unverified` and the run goes on.
- **`continue` after a report resumes in the same session.** After a report that ends with `resume=<run ticket>`, `continue` in any words puts the run ticket back in progress, re-queues its unfinished subtasks and starts the next round, with no second scout and no adoption step; an open Finish card counts as answered Keep.
- **No Finish card after a blocked stop.** A run that ends `blocked` (disk, worktree, a refused start) is about to be resumed, so it no longer offers a merge or a pull request. A typed push request still gets the card.
- **A second push updates the pull request.** When the branch already has a pull request, the run updates its title and body with `gh pr edit` instead of ending in `pushed, no PR`.
- **Standards files are found by listing, not by name.** The Workflow agent lists the markdown files in the repository's top folder and in `docs/` and judges each name, so a conventions file with any name reaches every dev node.
- **Page checks know widths and keep their tab.** `workflow-verifier` preloads `browser::resize` and `browser::screenshot`, its page-check rule gives the resize call for an expectation that names a width, and the tab lives as long as the check's deadline instead of ten minutes. A step and the read after it, or a run of key presses and their read, may go in one ordered `fp::batch` call. The critic and the review's refuters read the goal with `kanban::ticket::get`.
- **Work evidence carries the command as it ran.** A work node writes each command in `evidence` with the environment variables it set (a secret by name only), so the check starts from the invocation that worked.
- **Less bookkeeping for the Workflow agent.** `fp::batch` is preloaded, and a cost that reads null is written `cost unknown` and not read again.
- **No new requirement and no new argument.** The kit's worker list and its floors are unchanged.

## 0.1.8

- **A small goal no longer gets a board, tickets and a workflow run.** The Workflow agent sizes every goal first, with a few read-only calls, and says which path it took: `direct`, `focused` or `full`. A question, a lookup, a run-and-report, or a change of at most five files with one obvious way to do it, low stakes and a quick check is done by the agent itself: it writes in your checkout with guarded writes, commits only when your message asks for it and pushes nothing, runs one narrow check, and reports what it changed, what it ran and how to undo it. Until now every goal paid for a board project, a run ticket, a design run of ten nodes and four to six runs, a one-line config change included.
- **One or two tickets run focused.** No board (`board=on` keeps it), no design run when the place is known (explorers and a planner when it is not) and no baseline. A code ticket that runs alone is one run: an implementer node writes the code and its tests in the run worktree and the check loops it, with no ticket worktree, no cherry-pick and no separate tests run. A wave of several tickets keeps one worktree per ticket, the integration and the tests-and-check run.
- **The design run is sized.** `design=auto` now runs none when the agent can write the tickets from what it read, a lean one (explorers and the planner) when it cannot, and the panel of three competing designs with a refuter each only when the approach is a real choice that is costly to reverse, or the goal asks for a design. `design=on` is the panel. The explorers start from what the agent already found.
- **The review runs when it pays.** `critic` is now `auto`: the critic and its refuters run with two or more verified tickets, a hard ticket, or a goal that asks for a review. One ticket's check already reviewed the whole range. `critic=on` keeps the old behaviour.
- **A check loop that fixes nothing stops.** The verdict gains `stalled`: on a repeated pass the check first looks at its own last reasons, and when none is fixed it answers at once, without running the suite again, which ends the loop. The batch then gets one repair on the plan model with a root-cause brief, and a second stall parks its cards with the reasons. Before, the same reason came back for four passes and more.
- **Only a broken criterion fails a check.** "Any caveat is fail" is gone: a reason is an observation that breaks an Acceptance line, a project command or a review rule. A remark on how a test is written, when the test calls its entry point and can fail, is a note in `checks` and never changes the verdict; a finding about a test must name the code change that breaks the criterion and still passes the test.
- **A card gets a `Tests` bullet only when a regression test can observe its change** and the package already has tests of that kind. A change of looks, wording, configuration values or documentation is proved by its Verify calls, a page check included.
- **Nodes that change files have their own model stage.** `agents/workflow-models.md` gains a `code` column: code, solo and batch nodes run on Opus (claude-code) or `sol` (openai-codex), never one size down, since the smaller work model failed real work. The `work` stage keeps the explore nodes and plain research and gains the baseline, which only runs commands. With no row for the provider, only those nodes go one size down. A table edited before this release keeps working: a row with no `code` cell uses its `check` cell.
- **The orchestrator runs at medium reasoning effort.** Its turns are bookkeeping; design, planning, hard tickets and stalled repairs stay on the plan model at high.
- **Several goals in one session.** A message after a run's report, or after direct work, is a new goal and is sized again; a small follow-up to a kept run branch is committed on that branch. Runs of one session get distinct run ids and branch names (`-g2`, `-g3`).
- **Changed defaults:** `board` and `critic` are `auto`, and `design=auto` has three sizes. To get the previous behaviour for a goal, pass `board=on design=on critic=on`.
- **No new requirement and no new argument.** The kit's worker list and its floors are unchanged.

## 0.1.7

- **A card that changes a web page is checked in a browser.** When the `browser` worker is installed and finds a Chromium, the card's Acceptance carries a page check: a `Serve:` call that starts the project's own server in the worktree and a `browser::sessions::start` Verify call with the page's URL and what a person should see there, after which typing and clicks. The check opens the page in a private tab, uses it as the expectation says, reads the visible text and the page's console, and closes the tab and the server before it answers. An uncaught exception on the page fails the card; a `curl` of the HTML or a component test no longer counts as running the page the way its user does.
- **Research reads pages that render with JavaScript.** A work or check node whose fetch of a public page comes back without its text reads it with `browser::dynamic-fetch`, one call and no tab.
- **The browser is optional and never installed by a run.** The Workflow agent asks `browser::chromium::status` once per run and passes `Browser: available` or `Browser: unavailable (<reason>)` to every node. Without it, cards carry no browser call, a page criterion ends with `(not checked in a browser)`, and the run ticket's Notes say how to install it. No node downloads Chromium, Playwright or Puppeteer; a `chromium_missing:` error leaves the card unverified with that reason.
- **The browser contracts are preloaded.** `workflow-verifier` preloads the page-check calls (`browser::sessions::start`, `navigate`, `elements`, `act`, `console::read`, `sessions::stop`) and `browser::dynamic-fetch`; `workflow-worker`, and through it `workflow-planner` and `workflow-impl`, preloads `dynamic-fetch`, `sessions::start`, `elements`, `act` and `sessions::stop`. A node calls them on its first step, with no discovery. Without the browser worker the harness lists them as not available in that session, and nothing else changes.
- **No new requirement.** The kit's worker list is unchanged: add the browser with `iii call compose::add worker=browser`.

## 0.1.6

- **A provider hiccup no longer drops a design, refute or check node.** Every `workflow-planner` and `workflow-verifier` node (explore, design, refute, plan, check, batch check, baseline, critic and the review's refuters) is marked `read_only`. When its turn fails on a transient provider failure after the harness's own retries, the workflow worker waits a minute and continues it once in its own session, so the work it already did is kept and not paid again; the plan no longer runs on five of six inputs because one refuter hit a provider outage. Work, code and batch nodes change files or do the work itself, so a failure still fails them. The node keeps its `timeout_ms`, so a run's deadline timer is unchanged, and one that fails with less than 7 minutes of it left (at its deadline, say) still fails at once, since its continue would have no time to finish.
- **Requires** `workflow` 0.3.4 (the `read_only` node key; an older worker refuses every run) and `harness` 1.9.13 (`failure.retryable` on `harness::status`).

## 0.1.5

- **The batch check finds an already verified card's fallout by its landed commit.** Since 0.1.4 commits carry no ticket key, so the `In range:` line now gives each card's landed sha and the check looks it up with `git log --format=%H`.
- **An empty `plan_model` takes a given `check_model` before the model list**, as the arguments table says.
- **The automatic choice no longer skips past the next size down.** It finds the size right below the orchestrator's first, and stays on the orchestrator's model when that size is the smallest or has a smaller context window.
- **A model a start refuses does not use up the start's three sends** while its cell has another id, so every listed model gets a try.

## 0.1.4

- **The run picks a model per stage, from a list you can edit.** `agents/workflow-models.md` is a new kit file, data and not an agent: one row per provider and, for the plan, check and work stages, a list of model ids, best first; the file says which nodes each stage covers. With `models=auto`, the new default, a run whose orchestrator is on a listed provider gives each stage the first listed id its model catalog has and picks nothing outside the row; a stage with no listed id in the catalog runs on the orchestrator's model. The file ships filled in, and kit updates keep your edits.
- **A provider with no row gets a model per role.** There, the explore, work and code nodes and the batch's tests run one size below the orchestrator's model in its provider's current line-up, never on the smallest size. Every check (the baseline, the ticket and batch checks, the critic), the design, refute and plan nodes and the review's refuters stay on the orchestrator's model. The choice follows the node's role; the one exception is a ticket the plan marks hard. Under both, a profile pin and `work_model` / `check_model` / `plan_model` still win, and `models=own` restores 0.1.3: every node without a pin or a model arg on the orchestrator's model. A 0.1.3 run resumed on 0.1.4 gets the new default; pass `models=own` with the resume to keep it as it was.
- **The work model gets one round.** A ticket or batch that comes back for a retry, every ticket of the last round and the synthesis run on the check model, and a timeout on the work model is retried there instead of parked. When a start refuses a picked model, or every node of a run that used it fails with an error other than a timeout, that model is skipped for the rest of the run: only the stages that used it move, to the next id of their cell, else to the orchestrator's model, and the run ticket records `skip_models=<id>`, so a resume keeps it. A design run that loses its design, refute and plan nodes this way runs once more on the next plan model before the orchestrator plans the tickets itself. `skip_models=<ids>` is also an arg, for a model the catalog lists but the account cannot run. Without a row, the orchestrator stays on its own model when the next size down is the smallest or has a smaller context window, or when it cannot tell which size is right below its own.
- **A hard ticket runs on the plan model.** The plan marks a ticket whose work a smaller model is likely to get wrong the first time with a `Hard` bullet on its card, the reason in one clause. The signals are a closed list: the ticket writes state that parallel threads, processes or requests also write; it changes a permission check or handles a secret; it changes a stored format, migrates data or changes what existing callers of a public interface get; it has an invariant to hold, as a parser, a state machine or date or money arithmetic does; in the plain flow, its sources disagree. That ticket's work or code node runs on the plan model, the one that designs and plans the run, in every round, retries included, instead of failing once on the work model and spending a round; every other ticket, and the batch's tests, keep the work model. The orchestrator marks the same way when it writes the tickets itself or turns new items into cards. A profile pin and `work_model` still win, and `models=own` makes the mark moot. A resumed run reads the cards again, so the mark survives.
- **Commits and code never name a board ticket.** A code commit is the card's Commit subject as written, the batch's test commit names what it covers, the implementer writes no ticket key into a comment, docstring, test name or fixture, and the batch check flags one that slips in.
- **A resume reads the run's args before it resolves the models,** so a stored `models`, `skip_models`, `work_model`, `check_model` or `plan_model` applies. The run ticket's `Models` bullet names the plan, check and work models and where each came from: a pin, an arg, the list, the automatic choice or the orchestrator's own.
- **The run asks before it pushes, instead of refusing.** When the repository has a remote and the run branch has commits, the dev flow ends with a Finish card that offers to push the branch and open a pull request into the base, under `approve=auto` too; a goal or a message that asks for a push or a pull request gets the same card, and a goal that rules a push out gets no such offer. Only an answer that names the push or the pull request pushes: any other reply, or a dismissed card, keeps the branch. The run then pushes only its own branch and opens a ready pull request with `gh`, titled from the goal, with the run's report as its body. The card says when the push would also publish commits of the base that the remote does not have. Without `gh`, or when it is not signed in, the branch is pushed and the answer gives the command to run. A refused card keeps the branch, and the kit never pushes the base, watches CI or merges the pull request. The run ticket is settled and the report posted before the card, so an unanswered card leaves a finished run. With `approve=on` the card keeps Merge, Keep and Discard.

## 0.1.3

- **A new input form can still be a security decision.** Choosing how a new command takes a secret, or whether it writes without a confirmation, stays consequential and blocks when nobody can answer.
- **Every answer to the plan's questions reaches the tickets and the plan.** Answers the Workflow agent gave itself under `## Notes` rewrite the cards like a Design card answer does, and R's `## Plan` is rewritten to match, so the plan a user approves never describes a rejected choice.
- **Tickets are cut by behaviour.** When a goal is split, each ticket delivers one behaviour end to end and its own Acceptance shows it; one layer (the storage, the interface) is never a ticket. A refactor that several tickets build on comes first.
- **Tests go through the card's entry point.** A code card's **Tests** bullet names the entry point each case calls. The batch tests there, and the check refuses a test that copies the implementation or cannot fail. A dev card keeps its test paths out of **Files** and asks for no command run, so the implementer leaves tests and checks to the batch.
- **The batch check holds the change to the repository's written code rules.** In the dev flow, the files that say how the code is written (`CONTRIBUTING.md`, `CODING_STANDARDS.md`, `AGENTS.md`, a style or conventions file under `docs/`) go to every node. The implementer follows their rules about the code, and the batch check reports a broken rule as `standard:` with the rule quoted. Process rules, taste and what the lint already checks are never findings, and what a standard requires is never a lean defect.
- **A repair cannot silence the check that failed it.** A lint or type ignore, a looser check config, or a sleep or retry added so a test passes is a defect the batch check reports, unless a card asks for it.
- **Each dev card runs the change the way its user does.** At least one Verify call runs the behaviour itself (the command with its flags, or a one-line call of a library function), not only a test file.
- **A repeated check builds on its last verdict.** It first confirms each earlier reason is fixed and reviews only what changed in the cards it already passed.
- **The batch runs its own tests before it commits** and fixes what they show, so a repair pass is not spent on an error a short run already showed.
- **A standards file the change edits is judged as it was before the change.**
- **The Finish card names unverified commits** on the branch, so a merge choice is never made blind.
- **Plain results cite their sources.** Every claim in a plain ticket's result cites where the fact comes from (the code, the project's documents, official documentation, a command's output) or is marked `(unsourced)`, and the check opens the sources of the claims the ticket needs most.

## 0.1.2

- **A refused interview card covers only open decisions.** Answers already given stay; only a card refused because no human can answer turns the open decisions into assumptions, and a card refused for its shape is fixed and asked again.
- **Changing an existing interface stays consequential.** A new command, input form or output format can be assumed when nobody can answer; a change to an existing one is a compatibility decision and blocks.
- **A Design card answer reaches the tickets.** The plan's cards are rewritten where the answer changed them, so no ticket describes the rejected choice.

## 0.1.1

- **Reviews flag unneeded code.** The batch check, the critic and the design refuters treat code that should not exist or should be smaller as a defect: dead code, an option no caller sets, an abstraction with one implementation, a copy of an existing helper or of the standard library, a dependency for a few lines. Each one is proven with a read-only call and names the smaller form; what a card asks for, tests, input validation and error handling that prevents data loss are never flagged.
- **Interview before the plan.** Before it creates anything, the Workflow agent asks the decisions only the user can make, in rounds of one `harness::ask` card (up to four questions, each with a recommended answer first, at most three rounds): a round asks every decision whose prerequisites are settled, and facts are looked up, never asked. The answers are kept under the run ticket's `## Goal`, so every node and a resume read them. A session nobody can answer takes the recommendations and ends `blocked` only on a consequential decision (scope, compatibility, security, data loss, external cost).

## 0.1.0

- **New kit `iii/workflow`.** The ticket strategy of `iii/deepwork` (a run ticket, subtask cards, outcome labels, bounded rounds, a critic and a synthesized report) with every wave as one `workflow::start` run.
- **Phases are workflow nodes.** Each ticket's work and check are nodes with their own profile and model; a check's `fail` loops the work back with its reasons, up to `attempts` passes; a stuck node times out without stopping its siblings.
- **Design before tickets:** a design run explores the goal from three angles, writes three competing designs (minimal, robust, fit), refutes each, and a planner turns the survivors into the plan and the tickets; the review refutes each of its findings before it becomes a ticket. `design=auto` (the default) runs it only when the goal leaves the approach, the place or the size open, and records the decision and its reason on the run ticket; `on` always runs it, `off` never.
- **Dev flow:** a baseline node, one worktree per code ticket, integration on a `workflow/<slug>` branch, one tests-and-check run per integrated wave, repaired first in the next round when it fails, and a kept branch.
- **A board people can read:** the run ticket, cards and comments are markdown with short sections, checklists and short shas, and a goal is planned as a few reviewable tickets instead of many small ones.
- **The workflow is the record, the board the summary:** items stay in To do while they run (no `in_progress` moves), the board is read once per round, a retry writes nothing, the run pointer is one `state::set` per run, and `board=off` runs a small goal with no board at all.
- **Commit identity from git, never typed:** a work node reports the sha `git rev-parse HEAD` prints, and the check resolves the claimed sha with `git rev-parse --verify`, so a short or mistyped sha never fails correct work; commit messages and trailers are never criteria.
- **Installs beside deepwork:** its own profiles (`workflow*`), label `wf:run`, branches, worktrees and state scopes.
- **Requires** a `workflow` worker with the flat `workflow::start` request (`nodes` and `output` at the top level; `task`, `reads`, `schema` and `fanout` on a node), node options (`profile`, `model`, `label`, `phase`, `loop`, `filesystem_root`), an `output` that may name a loop body node, the caller folder, and the run-end notification: `workflow::start` returns the `harness::observe` call (`next`) for `workflow::on-run-completed` with args `{run_id}`, which replays a run that already ended.
